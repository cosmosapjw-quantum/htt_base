## 주요 설계 결정

### 1. SSOT re-use — 새 physics 없음

PR-010 Stage B 완료로 `source::registry` 가 이미 SSOT. MB-95 `production_source_v1` 이 이것을 호출 (L385-389). PR-024a 는 **같은 SSOT 을 호출** 하되 input 을 PSTF layout 에서 추출. 따라서 bit-identical 은 layout extraction 의 정확성에 좌우됨.

이 설계가 의미:
- PR-024a 의 "physics content" 는 거의 0 — SSOT 재사용
- 실질적 작업은 PSTF ↔ MB-95 layout 매핑의 정확한 port
- Bit-identical 보장은 `regression_source_*_matches_mb95` tests 가 SSOT 을 직접 호출하여 equivalence 검증

### 2. `VisibilityAtSnap` 새 struct 도입

MB-95 `VisibilityResult` 는 전체 η grid 를 보유하는 무거운 struct. PR-024a 는 단일 η 의 `g, gdot, gddot` 만 필요. Snapshot-level flat struct `VisibilityAtSnap` 을 도입하여:
- Unit test 독립성 (전체 visibility grid 없이 source 단위 test)
- PR-024b 에서 `VisibilityResult` 의 개별 snapshot 을 `VisibilityAtSnap::from_grid(vis, i)` 로 변환 가능
- `BackgroundQuantities` (PR-023a) 와 parallel API design

### 3. E-mode layout 차이 — P1 fix 발견

**Pre-audit 에서 놓친 문제**: PSTF E-mode layout (`lm_indexing.rs: n_photon_e = (lg+1)² − 4`) 은 **ℓ≥2 only**. `i_photon_e_m0(0)` 호출 시 assertion panic.

한편 MB-95 `CambLayout` 의 `e_mode(0)` 슬롯은 실제로 **production (Polter convention) 에서 사용 안 함**. `polter = 2·Θ_2/5 + 3·E_2/5` 이 E_0 를 포함하지 않음. `source_emode(EmodeConvention::Polter) = g · polter` 도 E_0 미사용.

**Fix (1회 iteration)**: `pstf_extract_source_inputs` 에서 `e0 = 0.0` 를 unconditional 로 설정. MB-95 의 E_0 값이 production output 에 기여하지 않으므로 bit-identical 유지.

이 fix 는 **data coincidence** — MB-95 의 E_0 가 0 이라서가 아니라, Polter convention 이 E_0 를 미사용하기 때문. PiBass convention (future PR) 사용 시 E_0 를 실제로 채워야 함. PR-024a 의 현재 scope 은 Polter 만이므로 `e0 = 0.0` 가 correct.

### 4. First-try streak 끊김 (5 → 0 reset)

PR-022b → PR-022c → PR-023a → PR-023b → PR-023c 의 **5 PR 연속 first-try success streak** 이 PR-024a 에서 끊김. 원인: layout convention difference 를 pre-audit 에서 식별하지 못함.

Lesson: Pre-audit §4 TDD gate forecast 가 10 tests 를 열거했으나, **layout-level edge case (E-mode ℓ<2 panic)** 은 검토 안 됨. Pre-audit quality 자체는 유지되었으나 — bit-identical contract 에 집중하여 structural invariant 를 놓침.

Future pre-audit 에는 "new file 이 touch 하는 모든 layout accessor 에 대해 ell range assumption 명시적 검토" 항목 추가 권장. STUCK_LOG.md 에 entry 추가 (P1 level, PR-024a 에서 catch).
