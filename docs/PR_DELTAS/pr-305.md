# PR-305 — trusted-launcher transaction pre-provisioning

## Scope and dependency

PR-305 starts from the durable PR-304 stack merge
`b9de03e16b1b60f4e36f62b49d968557ebb8553d`. It implements the source and
wire contracts for a future root-owned launcher, but does not install that
launcher or create execution authority.

The only executed end-to-end transaction is a disposable
`synthetic_fixture`. It uses ephemeral in-test Ed25519 keys, a temporary Git
candidate, a temporary nonce ledger, and a synthetic worker that opens no
observed payload. Synthetic receipts are structurally barred from production
consumers.

## Implemented transaction boundary

The standalone locked Rust crate under `tools/htt-auth-launcher` owns the
privileged boundary. Its release CLI accepts only `--contract` or
`--execute RUN_ID`; trust, candidate, nonce, run-store, and output-root paths
are compiled constants and have no caller-selected flags.

The transaction is fail-closed in this order:

1. require the root-owned launcher at its compiled deployment path;
2. inspect the exact candidate commit/tree through `/usr/bin/git` with a
   cleared environment and immutable object reads;
3. verify the externally provisioned root key and pinned fingerprint;
4. verify a detached Ed25519 signature over the exact registry-blob hash,
   candidate commit/tree, domain, version, time, and root key identity;
5. verify the active lane authority and exact human authorization receipt;
6. independently replay the ordered PR-289 record IDs and admission bundle;
7. rebuild the model, runtime, computed-rank, normalization, execution-plan,
   runtime executable, and candidate-worker blob bindings;
8. acquire the run lock, atomically consume the nonce with
   `O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC`, and fsync file plus directory;
9. write and fsync a start receipt with `observed_bytes_opened=false`;
10. materialize the bound candidate blob in root-owned read-only staging and
    launch it only as a dedicated nonroot worker with cleared supplementary
    groups, `no_new_privs`, and a fixed environment;
11. record one fsynced terminal receipt for success, error, timeout, or signal.

Candidate Python contains non-authoritative schema parsing only. It cannot
verify a live authority, consume a nonce, spawn a worker, or open data.

## Acceptance and hostile gates

The Rust suite covers canonical/duplicate-key rejection, external-root and
human Ed25519 verification, pending-registry refusal, Git path containment,
exact execution bindings, atomic nonce reuse and partial-entry refusal,
start-before-worker tokenization, output locking, environment isolation,
four terminal paths, production/synthetic separation, and a complete
synthetic transaction rehearsal.

The Python suite checks the six closed-world wire schemas, content identities,
resume drift, terminal semantics, the compiled fixed-path contract, rejection
of every path-override probe, absence of private production keys, exact
transaction ordering, exact PR-289 source preservation, and the zero-authority
terminal state.

The required clean-clone CI job formats, tests, and release-builds the locked
launcher, executes every PR-305 policy command, replays the PR-304 boundary,
and uploads only a seven-day `synthetic_fixture` launcher build plus an
uninstalled manifest. A CI artifact is rehearsal evidence, not an install or
execution authority.
