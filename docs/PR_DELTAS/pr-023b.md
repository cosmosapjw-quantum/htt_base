## 주요 설계 결정

### 1. Thomson drag 중복 적용 방지 (pre-audit §6 trigger 1)

MB-95 `camb_rhs:486-487`:
```
vbdot = -h·vb + cs2b·k·clxb + opac·(3·theta(1) - vb)/r_b
        └── PR-023b 부분 ──┘   └── PR-022b 에 이미 있음 ──┘
```

PR-023b `pstf_fluid_rhs` 는 **앞 두 term 만** 구현. PR-022b `pstf_thomson_collision` 이 **세 번째 term** 을 additive 로 같은 `dy[i_baryon_v_m0()]` 슬롯에 추가. PR-023c 에서 합쳐져 full MB-95 와 bit-identical.

`identity_vbdot_matches_mb95` test 의 주석 "WITHOUT the Thomson drag term (drag is in PR-022b)" 가 이 설계를 명시.

### 2. Option B interface — `FluidInputs` 에 `hdot` 직접 주입

```rust
pub(crate) struct FluidInputs {
    pub(crate) k: f64,
    pub(crate) h_conformal: f64,
    pub(crate) cs2b: f64,
    pub(crate) hdot: f64,    // PR-023a pstf_hdot() 결과
}
```

Caller 가 `pstf_hdot(state, v_b, &metric_inputs, layout)` 를 먼저 compute 하여 `FluidInputs.hdot` 에 주입. Option A (`FluidInputs` 가 `MetricInputs` 를 포함) 대비 장점:
- Test 독립성 — fluid RHS 를 metric 없이도 단위 test 가능
- Inter-sector dependency 를 API 레벨에서 명시
- PR-023c dispatcher 에서 `hdot` 을 한 번만 compute 하여 여러 sector (fluid + photon/ν ℓ=0 via `metric_monopole_source`) 에 재사용 가능

`regression_with_pr023a_hdot` test 가 Option B 의 integration 을 검증 — PR-023a `pstf_hdot()` 호출 → PR-023b fluid RHS → MB-95 bit-identical.

### 3. Synchronous gauge: v_c = 0

CDM velocity `v_c` 는 synchronous gauge 정의상 identically zero. PR-023b `pstf_fluid_rhs` 는 `dy[i_cdm_v_m0()]` 에 **쓰지 않음** (sync gauge 조건). `caveat_cdm_velocity_zero_at_sync_gauge` test 가 pre-fill sentinel 42.0 유지로 검증.

이것은 미래 gauge transformation 시 explicit 처리 필요 ("synchronous → conformal Newtonian" 또는 "synchronous → hypersurface orthogonal tilt" 시 v_c ≠ 0 가 발생). Phase 4 Bianchi tilt 에서 재검토 예정.

### 4. New layout accessors

Layout 에 4 accessor 추가:
```rust
i_baryon_delta()  = baryon_start + 0
i_baryon_v_m0()   = baryon_start + 2    ← PR-022b, PR-023a 에서 raw 로 썼음
i_cdm_delta()     = cdm_start + 0
i_cdm_v_m0()      = cdm_start + 2       ← v_c = 0 at sync gauge
```

PR-022b `collision.rs` 와 PR-023a `metric.rs` 에서 `baryon_start + 2` 를 raw 로 사용했던 부분을 `i_baryon_v_m0()` 로 치환 가능 (optional refactor). **PR-023b 에서는 치환하지 않음** — 기존 code 그대로 유지 (PR-023c 또는 별도 cleanup PR 에서 고려). 이것은 scope creep 방지.
