## Fingerprints, flattening, and multiplicity

Each contract carries a content-addressed **estimand fingerprint** (over
all fields; any edit mints a new one) and a **channel fingerprint** (over
the specification fields minus `analysis_id`/lineage). Registering two
distinct ids with identical specification content is refused as channel
flattening — reachable through the PUBLIC API, not an internal poke. An
in-place edit (same id, changed fields) is refused; a rename revision
must NAME its predecessor via `supersedes` AND declare a distinct
`prior_null_multiplicity`, and the registry bumps the look-elsewhere
multiplicity count (`multiplicity()` = 1 original, +1 per revision).
Superseding an unregistered predecessor is refused.

## Named dependence + branch separation

Dependence is recorded as a NAMED cluster; the independence guard
(`_names_independence`) normalizes underscore, hyphen, and space
separators, so "assumed-independent", "iid gaussian", and
"independent-rows" all require an explicit justification (never the
silent default) while a genuinely correlated cluster does not falsely
trip. The dependency graph groups analyses by cluster. The
deterministic template-mean and stochastic covariance-factor generative
branches are separate typed objects; `compose_generative_model` refuses
wrong-role composition (mean-as-cov, cov-as-mean) and cross-analysis
mixing.
