### Non-blocking notes (suggested fixes)
1. **The typed contract only partly separates the inputs.**
   - `CalibratedDerivativeChannel` holds only Tr, q, the germ, q0, q̇ and regularity.
   - It has no fields for κ/ℓ calibration, the remainder modulus M, source identification, the non-rotating frame or the optical D.
   - `g14aSupplyLedger` is a record that no theorem references.
   - The name "Calibrated" therefore overstates the structure. Suggested fix: rename it to `TransportedDerivativeChannel`, or add `κ ℓ : ℝ`, `cal : κ/ℓ = 1` and an `M`-bound field. In either case, add a table in SOURCE_RECOVERY mapping each ledger field to the Lean hypothesis that discharges it.
2. **T8 is narrower than its note suggests.** It proves non-identifiability only from single-event zeroth-order data (p, U(p)). The AUTHOR_RETURN note says "a static remote snapshot factors through zeroth-order data", but a multi-source snapshot has multi-event, past-null data. Its real deficits are the missing transport, identification and baseline/clock calibration, which T3's untransported bias and calibration-scaling controls address. Reword the note; the pitfall is respected because nothing synthesizes a derivative, not because T8 covers remote snapshots.
3. **T5 has no bound on e.** `proper_motion_decomposition` is an algebraic identity with the remainder e unconstrained, so it gives no quantitative J estimate from proper motion. That is consistent with the acceptance criteria, but state explicitly that no remainder bound is provided.
4. **Calibration is modelled as one scalar factor κ/ℓ.** Anisotropic, offset or direction-dependent miscalibration is not covered.
5. **The remainder bound is not instantiated.** `finiteBaseline_remainder` is generic in f and is not linked to `transportBack`. It also gives M·s rather than the sharp M·s/2; the author discloses the latter.
6. **SOURCE_RECOVERY gaps.** It records HEAD 9f0beb69 but does not list that commit's astrometry E/B fits among the excluded remote proper-motion routes. It also cites the Main.lean hash in RETURN.json, while the hash is actually in `lean/result.json` and the manifests.
7. **Oleans are not bitwise reproducible across source directories, though kernel acceptance is.**
   - PortCas01 and VelocityJetRest rebuild bit-identically.
   - Main gave `7ee5aafb…` (recorded `148b84df…`); VelocityJetDecomposition gave `d80c9966…` (recorded `31a5386d…`).
   - G14AVelocityChannel gave `902fd8a4…` (recorded `12bd42ed…`).
   - Build identity should therefore be tied to source hashes and kernel acceptance, not to olean hashes.
8. **Style only:** deprecation warnings on `ContinuousLinearMap.neg_apply/add_apply` and a `<;>` linter note.
